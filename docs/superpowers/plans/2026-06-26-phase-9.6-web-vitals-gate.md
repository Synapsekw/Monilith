# Phase 9.6 — Web-Vitals gate (closes Phase 9)

**Status:** approved (scope fixed by the Phase-9 spec; no interactive brainstorming)
**Date:** 2026-06-26
**Spec:** `docs/superpowers/specs/2026-06-22-phase-9-performance-optimization-design.md` §9.6
**Branch:** `task/web-vitals-gate`

## Goal

Close Phase 9 with the dual-layer measurement gate the spec calls for: **synthetic** budget
enforcement on CI (Lighthouse CI) + **real-user** Web-Vitals instrumentation (RUM) wired into the
app. The budget below is the Phase-9 acceptance gate.

## The budget (from spec §"Success budget")

| Metric                | Target               |
| --------------------- | -------------------- |
| TTFB                  | < 200 ms             |
| LCP                   | < 1.5 s              |
| INP (interaction)     | < 200 ms             |
| CLS                   | < 0.1                |
| First-load JS / route | meaningful reduction |

Lighthouse (lab) cannot measure INP (it needs real interaction) — it reports **TBT** as the lab
proxy, plus **LCP / CLS / TTFB (server-response-time) / total byte + script weight** as the
first-load-JS proxy. So the `.lighthouserc.json` asserts:

- `largest-contentful-paint` ≤ 1500 ms (LCP)
- `cumulative-layout-shift` ≤ 0.1 (CLS)
- `server-response-time` ≤ 200 ms (TTFB)
- `total-blocking-time` ≤ 200 ms (lab proxy for INP responsiveness)
- `resource-summary:script:size` budget for first-load JS (script bytes)
- category `performance` score floor

INP itself is covered by the **RUM** layer (field data), which is the correct place to measure it —
documented in the plan as the division of responsibility.

## Layer 1 — Lighthouse CI (synthetic)

- `.lighthouserc.json` at repo root: `collect` (3 runs/route, median), `assert` (budget above as
  `assertions`), `upload: temporary-public-storage`.
- Routes: `/` (static landing — the one route that is deterministic and auth-free in CI). The
  authenticated board page needs a logged-in session + live Supabase, which CI does **not** have
  (placeholder env, RLS auto-skips) — running it would be flaky and meaningless, so it is **scoped
  out of CI** and left to the RUM layer + local runs. This is the "scope it sensibly and document
  the choice" path the task allows.
- New CI job `lighthouse` in `.github/workflows/ci.yml`: build with placeholder public env (same as
  `verify`), `lhci autorun` (it starts `next start` via `startServerCommand` and waits on the URL).
  The `assert` step **fails the job** when any budget assertion regresses — that is the gate.
- New `package.json` devDep `@lhci/cli`; convenience script `lhci`.

## Layer 2 — Real-user Web-Vitals (RUM)

- `src/components/web-vitals.tsx` — `"use client"`, uses `useReportWebVitals` from `next/web-vitals`
  (confirmed against `node_modules/next/dist/docs/.../use-report-web-vitals.md`). Renders `null`.
  - Dev: `console.debug` the metric (name/value/rating).
  - Prod: if `NEXT_PUBLIC_WEB_VITALS_ENDPOINT` is set, `navigator.sendBeacon` (fallback `fetch` with
    `keepalive`) the metric JSON; otherwise no-op. Minimal, correct, no new analytics dependency.
  - Stable callback reference (module-scope handler) per the Next.js doc's duplicate-reporting note.
- Wire `<WebVitals />` into `src/components/providers.tsx` (already a client boundary used by the
  root layout) so it is mounted app-wide.
- Add optional `NEXT_PUBLIC_WEB_VITALS_ENDPOINT` to `src/lib/env.ts` (optional string; absent ⇒
  no-op sink).

## Data-fetching budget (working-agreement #5)

RUM component does **0 server round-trips** on render; it only fires a beacon on metric events
(post-paint, non-blocking, `sendBeacon`). No RSC nav, no refetch. Not applicable to the CI config.

## Tests (TDD)

`src/components/web-vitals.test.tsx`:

1. Registers a stable callback with `useReportWebVitals` (mock `next/web-vitals`).
2. Dev mode → `console.debug` called with the metric.
3. Prod mode + endpoint set → `navigator.sendBeacon` called with the endpoint + serialized metric.
4. Prod mode, no endpoint → no beacon, no throw (no-op sink).
5. Renders `null`.

`src/lib/lighthouserc.test.ts` (or colocated): parse `.lighthouserc.json`, assert it is valid JSON
and encodes each budget threshold (LCP 1500, CLS 0.1, TTFB 200, TBT 200, script-size budget,
category floor) — so a budget edit can't silently drop an assertion.

## Gates (local, this task)

`pnpm typecheck && pnpm lint && pnpm test --project unit && pnpm build`. (Full integration suite
skipped per task instructions; `lhci` is exercised in CI, optionally dry-run locally.)

## Execution DAG

Single-task, single-agent (this is the closing leaf 9.6 of the Phase-9 DAG; nothing depends on it).
Files are independent: RUM component + test, env tweak, `.lighthouserc.json` + test, CI job,
`package.json`. Built in one pass, no parallel batches.

## Out of scope

- Authenticated-route Lighthouse runs in CI (needs live session; left to RUM + local).
- A real analytics backend (sink is endpoint-or-noop; wiring a vendor is a separate task).
- INP lab measurement (field-only by nature; covered by RUM).
