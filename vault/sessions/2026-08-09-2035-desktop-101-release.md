# Desktop 1.0.1: the version stopped lying, and the release shipped

Continues [[2026-08-09-1756-desktop-manual-update-path]]. That built the prompt; this made the
number it compares trustworthy, then cut the first real release.

## What changed

**`monolith-desktop` (`dd5e77b`, `f11f4db`, `26c4cd8` — 16 commits, still no remote):**

- **The shipped version was hand-maintained.** `SHELL_VERSION = "1.0.0"` sat in `config.ts` while
  `package.json` carried its own, with **nothing syncing them** — and they fed different things:
  package.json drives artifact names, `latest-mac.yml` and Info.plist; the literal drove the gate
  and every prompt comparison. Shipping 1.0.1 would have produced a build reporting itself as
  1.0.0, offering an update to what the user already had, **forever**, with About Monolith and the
  update dialog disagreeing inside one app. Latent only because both strings read 1.0.0.
- **Fixed by injection, not import.** `checkVersionGate(currentVersion)` takes the version as an
  argument; `app.getVersion()` is read in the one module that already depends on Electron.
  Importing it into `version-gate.ts` would have dragged the runtime into comparison logic that is
  unit-tested under plain Node.
- **The preload exposes `version`**, via `webPreferences.additionalArguments` read off
  `process.argv` — a sandboxed preload cannot reach `app` at all, and `ipcRenderer.sendSync` would
  block the renderer on every load for a constant.
- **1.0.1 built, published and verified**, and the publish script gained a real verification —
  [[2026-08-09-gotcha-87-a-read-straight-after-a-write-is-not-a-verification]].

**This repo (`9ce176c2`, `32a93e68`):** Settings shows **"Latest version X"** (the bare word was
ambiguous read inside the app) plus **"You're running X — up to date / update available"**, and the
bridge finally has one typed definition in `src/lib/desktop/bridge.ts` instead of an inline cast
per call site. `desktop-release.json` bumped to `latestShell: 1.0.1`.

## Why

A version the app maintains by hand is a number that will eventually disagree with itself, and this
one was one release away from doing so — in the exact subsystem whose whole job is comparing
versions.

## The fix caught itself

Changing to `app.getVersion()` turned the dialog fixture red immediately: run as
`electron <file>` there is no app package.json, so it returns **Electron's** version (43.x). That is
precisely the class of mistake being replaced. The fixture now pins the version and gained a case
asserting a build **newer** than the feed is offered nothing — it fails if anyone hardcodes again.

## How to test (for the user)

1. `curl -s https://www.monolith.works/desktop-release.json` → `latestShell: 1.0.1`, 1.0.1 DMGs.
2. `curl -sL https://releases.monolith.works/desktop/latest-mac.yml` → `version: 1.0.1`.
3. `cd ~/Dev/monolith-desktop && pnpm install:local`, launch → **Monolith → Check for Updates…** →
   _"You're up to date"_.
4. Settings → Integrations → Desktop app → **"You're running 1.0.1 — up to date."**
5. Turn off Wi-Fi, check again → _"Couldn't check for updates"_, never "up to date".

## Open threads

- **1.0.0 installs cannot be reached by the app.** They predate the prompt and do not expose
  `version`, so they neither announce 1.0.1 nor populate the Settings line — correctly rendering
  nothing rather than guessing. One manual reinstall puts each user on the self-announcing track.
- **16 commits, no git remote.** Now including a published release. `gh repo create` is blocked by
  the permission classifier; needs the owner. This is the largest standing risk in the desktop work.
- Auto-update still cannot **install** — unchanged, gated on the Developer ID.
- The four lock-bound smoke tests need `/Applications/Monolith.app` quit; that is the
  single-instance lock (`index.ts:22`), not a defect. Verified twice by isolation.
